# Архитектура v1

Tutor CRM — модульный монолит: отдельные frontend, backend API и worker используют одну PostgreSQL. Доменные модули backend разделяются по бизнес-областям и общаются через явные сервисы и transactional outbox.

Приложение рассчитано на одного преподавателя. Любой приватный API проверяет роль, а student API связывает выборку с профилем текущей серверной сессии. Файлы хранятся в приватном S3 и выдаются только после проверки доступа API.

Web и API в production должны работать под одним origin. Это упрощает cookie-сессии и CSRF-защиту. Локально сервисы используют разные порты с явно разрешённым origin.

PostgreSQL является источником истины для расписания и денег. Пересечения интервалов и уникальность финансовых операций защищаются ограничениями базы, а прикладной слой возвращает понятные ошибки.

Повторяющиеся уроки материализуются на ограниченный горизонт и достраиваются worker идемпотентно. Перенос урока оформляется отдельным запросом: расписание меняется только в транзакции принятия после повторной проверки доступности и конфликтов.

Домашнее задание связано с уроком один-к-одному, финальный ответ — с заданием
один-к-одному. Состояние домашней работы вычисляется из наличия этих записей и
не хранится отдельным изменяемым полем. Файлы ответа сначала связаны с заданием
как приватный черновик ученика, а при создании submission атомарно переводятся
на него.

Финансовый контур хранит тариф отдельно от будущих снимков начислений. Все
суммы представлены `NUMERIC`/`Decimal`; float не используется. Изменение тарифа
не должно пересчитывать уже выпущенные invoices. CRM ведёт ручной учёт
начислений и подтверждений, не принимает и не переводит деньги.

Заявление ученика об оплате отделено от подтверждённого payment. Остаток invoice
вычисляется как `total - sum(payment_allocations)`, а отчёт о поступлениях — по
payments. Исправление создаёт обратные payment/allocation и сохраняет исходную
операцию; hard delete финансовых записей отсутствует.

Доменные сервисы добавляют уведомления через transactional outbox до commit.
Worker атомарно материализует внутреннее уведомление, ведёт число попыток и
backoff, а уникальные ключи исключают повторную доставку. Фоновая проверка
просроченных invoices создаёт одно напоминание на начисление. Email и Telegram
остаются отключёнными адаптерами; обязательный канал v1 работает внутри CRM.

Пробная заявка поступает через единый intake service, поэтому будущий адаптер
не должен менять workflow. Web-адаптер не собирает контакты: только ФИО, класс
и необязательные учебные пожелания. Подтверждённый слот сериализуется через ту
же блокировку преподавателя, что создание урока, а PostgreSQL исключает
пересечение пробных заявок. Конвертация после проведённого занятия одной
транзакцией создаёт ученика, приглашение и связь с исходной заявкой.

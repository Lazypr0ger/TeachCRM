# Исправление загрузки файлов домашних заданий

Дата проверки: 20 октября 2026 года. Ветка: `devRem`.

## Воспроизведение до исправления

Проверка выполнялась по реальному пользовательскому маршруту: Next.js на `127.0.0.1:3000` проксировал запросы в FastAPI, данные сохранялись в PostgreSQL 17, а объекты — в приватный bucket LocalStack S3 с включённым versioning.

1. Преподаватель создал ученика, урок и задание.
2. Ученик вошёл по созданной учётной записи.
3. `POST /api/v1/files/upload-init` вернул `201`.
4. Multipart-загрузка в `/api/v1/files/upload-tickets/{id}/content` вернула `204`, объект появился в S3.
5. `POST /api/v1/files/upload-complete/{id}` вернул `409` с текстом `Не удалось завершить загрузку`.
6. PostgreSQL записал точную причину: `file_links_file_id_fkey` — `file_id` отсутствовал в таблице `files` в момент вставки связи.

## Точная причина

В `backend/app/modules/files/service.py`, в функции `complete_upload`, экземпляры `StoredFile` и `FileLink` добавлялись в одну SQLAlchemy-сессию без объявленной ORM-связи между моделями. Поэтому unit-тесты на SQLite проходили, а PostgreSQL мог выполнить `INSERT INTO file_links` раньше `INSERT INTO files` и отклонял транзакцию по внешнему ключу.

Проблема находилась после копирования временного S3-объекта в постоянный ключ и до фиксации метаданных. Статус задания не становился `ACCEPTED`, но пользователь не мог завершить ни одну файловую загрузку.

## Исправление

- После добавления `StoredFile` выполняется явный `db.flush()`, и только затем создаётся `FileLink`. Родительская строка теперь гарантированно существует до проверки внешнего ключа PostgreSQL.
- В тестовом SQLite включены внешние ключи, чтобы дальнейшие ошибки порядка записи обнаруживались локально.
- Ученик выбирает сразу несколько файлов, видит имя, размер и состояние каждого, может удалить файл до отправки. Загрузка начинается только после явного нажатия кнопки окончательной отправки.
- При частичном сетевом сбое уже загруженный файл остаётся в очереди по своему ID и не загружается повторно. Текст ответа остаётся в форме; `ACCEPTED` устанавливается только после успешного финального запроса.
- Клиент до обращения к серверу проверяет общий лимит 10 файлов, допустимое расширение и размер 1 байт–15 МБ. Сервер продолжает проверять magic bytes, имя, размер, владельца, роль и целевой объект.
- Ошибки API обрабатываются и для не-JSON ответа proxy/backend, поэтому вместо исключения JSON parser пользователь получает понятное сообщение.

## Ограничения

- Поддерживаются PDF, PNG, JPEG, WEBP и DOCX; исполняемые и неизвестные форматы запрещены.
- Лимит — 15 МБ на файл и 10 файлов на объект. Файлы находятся в приватном S3, а скачивание проходит через авторизованный endpoint.
- Камера и системный picker доступны через обычный мобильный `input type=file` с `accept` и `multiple`. Физическая проверка на iPhone Safari и Android Chrome остаётся ручным пунктом приёмки, поскольку в текущей среде нет мобильных устройств.

## Автоматические проверки

- Backend: сценарии файлов и домашних заданий проверяют PDF + PNG + текст, точное совпадение скачанных байтов, идемпотентность финальной отправки и запрет доступа другого ученика.
- Frontend: тесты проверяют несколько выбранных файлов, расширения, пустой/слишком большой файл и лимит количества.
- Полный набор статических проверок, unit/integration-тестов и production build запускается перед фиксацией этапа.

## Проверки безопасности

- Загрузка и завершение требуют действующую сессию и CSRF-токен.
- Ученик может прикреплять файлы только к собственному заданию и до окончательной сдачи.
- Черновой файл до сдачи скрыт от преподавателя; после сдачи доступен преподавателю и ученику-владельцу.
- Другому ученику работа и скачивание возвращают `404`, не раскрывая факт существования объекта.
- Bucket не публичный; URL скачивания не является статическим публичным адресом.

## Коммит

Этап фиксируется коммитом `Исправлена передача файлов домашних заданий`. Хеш добавляется в отчёт этапа после создания коммита.
